# Контракт базы и API

Приложение читает четыре таблицы через Supabase Data API. Все изменения объектов и задач выполняются семью RPC. Каждая RPC возвращает JSON-объект изменённой строки (`jsonb`, не массив); при удалении возвращается строка с заполненным `deleted_at`.

## Таблицы

- `profiles`: `id`, `full_name`, `role` (`manager` / `executor`). UUID соответствует `auth.users.id`. Профили создаёт доверенный администратор; исполнитель читает только собственный, постановщик — все.
- `projects`: `id`, `name`, `address`, `created_at`, `deleted_at`.
- `tasks`: `id`, `project_id`, `title`, `description`, `assignee_id`, `status`, `author_id`, `author_name`, `created_at`, `deleted_at`.
- `task_status_history`: `id`, `task_id`, `from_status` (допускает `null` при создании), `to_status`, `actor_id`, `actor_name`, `created_at`, `comment`.

Все ID — UUID, даты — `timestamptz`. Статусы (`public.task_status`): `new`, `in_progress`, `review`, `accepted`, `rework`. Имена FK для связей Supabase: `tasks_project_id_fkey`, `tasks_assignee_id_fkey`, `tasks_author_id_fkey`. Автор и участники истории сохраняются со снимком имени, полученным базой из профиля; клиент эти поля не задаёт.

## RPC

| Функция | Именованные параметры | Доступ |
| --- | --- | --- |
| `create_project` | `p_name`, `p_address` | Постановщик |
| `update_project` | `p_project_id`, `p_name`, `p_address` | Постановщик |
| `archive_project` | `p_project_id` | Постановщик |
| `create_task` | `p_project_id`, `p_title`, `p_description`, `p_assignee_id` | Постановщик |
| `update_task` | `p_task_id`, `p_project_id`, `p_title`, `p_description`, `p_assignee_id` | Постановщик |
| `archive_task` | `p_task_id` | Постановщик |
| `transition_task` | `p_task_id`, `p_expected_status`, `p_new_status`, `p_comment = null` | Проверяется по переходу и назначению |

Название объекта/задачи обязательно, до 200 символов; адрес обязателен, до 500. Описание допускает пустую строку, до 10000 символов; `null` преобразуется в пустую строку. Комментарий — до 10000 символов. Строка только из пробельных символов не считается заполненной. Исполнителем можно назначить только профиль с ролью `executor`.

Допустимые переходы: исполнитель своей задачи `new → in_progress`, `in_progress → review`, `rework → in_progress`; постановщик `review → accepted` либо `review → rework`. Для доработки необходим непустой комментарий. База блокирует строку задачи, проверяет ожидаемый статус, меняет статус и добавляет историю в одной транзакции. Создание добавляет событие `null → new`. Редактирование, перенос и переназначение не меняют статус, автора и дату создания.

Коды ошибок: `42501` — недостаточно прав; `P0002` — ресурс отсутствует, удалён либо недоступен; `22023` — недопустимые данные/переход; `P0001` — ожидаемый статус устарел, нужно перечитать карточку. Неизвестное значение enum может отклоняться стандартным кодом Postgres `22P02` до входа в функцию.

## Защита и удаление

RLS включён для каждой таблицы. Постановщик видит все активные объекты и задачи. Исполнитель видит только назначенные ему задачи, связанные с ними объекты и историю. Счётчики и вложенные выборки также ограничены RLS. После переназначения прежний исполнитель сразу теряет доступ при следующем запросе.

У `anon` нет доступа к таблицам и RPC; у `authenticated` есть только чтение таблиц и выполнение перечисленных RPC. Прямые записи в задачи, объекты и историю запрещены даже для API-роли `service_role`; доверенный администратор использует её только для создания профилей и проверочного чтения. Владельцы базы с SQL-доступом остаются доверенными администраторами. Роли читаются из защищённой таблицы, а не из изменяемых пользовательских метаданных.

Публичные RPC — `SECURITY INVOKER`; внутренние реализации — `SECURITY DEFINER` в схеме `private`, с фиксированным пустым `search_path`. Схему `private` нельзя добавлять в список Exposed schemas. Внутренняя реализация самостоятельно проверяет `auth.uid()` и права. Секретный ключ не нужен работающему фронтенду.

Удаление — мягкое, без восстановления в интерфейсе. Удаление объекта в одной транзакции скрывает объект и все его активные задачи; история физически сохраняется. При создании/переносе задачи целевой объект блокируется и проверяется на активность, поэтому параллельное удаление не оставит в нём активную задачу. Политика задач не обращается обратно к объектам; зависимости RLS не образуют циклов.

Открытая регистрация и анонимные входы отключаются отдельно в настройках Supabase Auth. SQL-миграция не меняет облачные настройки Auth. Пользователи сначала создаются через Auth Admin/Dashboard, затем администратор добавляет их профили; автоматического повышения роли из метаданных нет.

# Объекты и задачи

Мини-CRM строительной компании: объекты, назначенные задачи, приёмка и защищённая история статусов.

**Приложение:** https://work-search.ru

**Стек:** React + TypeScript + Vite, Mantine, React Router, TanStack Query, Supabase Auth/Postgres. Контейнер Caddy отдаёт статическую сборку; существующий Nginx на VPS завершает HTTPS.

## Локальный запуск

Нужен Node.js 22.12+ (проект собран на Node.js 24).

```sh
npm ci
cp .env.example .env
# В .env заполните VITE_SUPABASE_URL и VITE_SUPABASE_PUBLISHABLE_KEY.
npm run dev
```

В PowerShell вместо `cp` можно использовать `Copy-Item .env.example .env`. Производственная сборка: `npm run build`. Локальная проверка сборки: `npm run preview`.

## Настройка Supabase с нуля

1. Создайте отдельный проект Supabase.
2. Примените SQL из `supabase/migrations/` в порядке имён через SQL Editor или систему миграций Supabase. Миграция должна выполняться целиком в одной транзакции.
3. В Authentication → Sign In / Providers выключите **Allow new users to sign up** и анонимные входы. Email/пароль оставьте включёнными. Укажите URL приложения в Authentication → URL Configuration.
4. Схема `private` не должна входить в список exposed schemas Data API. Для API используется только `public`.
5. Заполните публичные переменные из `.env.example`. Секретный ключ нужен только локальному скрипту подготовки демо и проверки сохранённых удалённых записей.

### Тестовые данные

Заполните локальные `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, затем:

```sh
npm run seed
npm run test:api
```

Скрипт создаёт двух постановщиков, двух исполнителей, три объекта и восемь задач во всех пяти статусах. Он выполняет переходы от имени соответствующих пользователей через те же RPC, что приложение. Пароли случайные и сохраняются только в `.demo-credentials.json`; повторный запуск сохраняет доступы. Этот файл не попадает в Git или образ Docker.

Пользователей также можно создать вручную в Authentication → Users; администратор добавляет в `profiles` соответствующий UUID, `full_name` и `role` (`manager` или `executor`). Обычный API-клиент не может назначать или менять роли.

## Как защищены данные

- Все четыре таблицы защищены RLS. Постановщики читают активные записи, исполнители — только назначенные им задачи, связанные объекты и историю этих задач.
- Пользовательский API имеет только чтение таблиц. Изменения проходят через семь RPC; их закрытые реализации проверяют действующего пользователя и права.
- Статус меняется под блокировкой строки. Проверка перехода, изменение задачи и запись истории составляют одну транзакцию; устаревший статус вызывает ошибку.
- История не имеет API для ручного добавления, редактирования или удаления. Автор, время и имена в истории формируются базой.
- Удаление мягкое. Удалённые задачи и объекты исчезают из интерфейса, а записи и история остаются в базе.
- Роль берётся из защищённого профиля, а не из изменяемых метаданных пользователя. Переназначение сразу меняет права доступа.
- Браузер получает только `VITE_SUPABASE_URL` и publishable key. Секреты и SSH-доступы исключены из Git и контекста Docker.

Детали RPC: [контракт базы](docs/db-contract.md). [Решения и допущения](docs/decisions.md). [Объяснение руководителю](docs/for-manager.md). [Развёртывание](docs/deployment.md).

## Проверки

`npm run build` проверяет TypeScript и производственную сборку. `npm run test:api` выполняет интеграционные проверки на выделенном проекте Supabase с обычными пользовательскими сессиями: изоляция данных, допустимые и запрещённые переходы, обязательный комментарий, подмена истории и роли, переназначение, мягкое удаление и конкурентные операции. Проверки создают временные записи и мягко удаляют их после выполнения.

Секретный клиент не используется для доказательства RLS; он нужен только для проверки, что скрытые после удаления записи физически сохранились. Для публичной проверки приложения используются выданные отдельно тестовые доступы.
